# Production Deployment & Operations Runbook: v3.38.0

**Scope**: Hardware Radar, IoT Telemetry Mesh, Smart Gates, Edge Biometrics & Voice Copilot V2  
**Target Release**: `v3.38.0`  
**Classification**: Production Engineering Standard Operating Procedure (SOP)

---

## 1. Release Architecture & Service Topology

The `v3.38.0` release introduces high-frequency event ingestion and WebSocket audio streams alongside the core Next.js 16 microservices:
1. **IoT Telemetry Ingestion Worker**: Multi-row buffered write-behind batching (`5,000 pkts/s`).
2. **Turnstile Gate Verification**: Sub-50ms transit checking with 5-tier Anti-Passback state evaluation.
3. **Voice Copilot Audio Mesh**: Duplex WebSockets with 16kHz PCM frame parsing and RMS voice activity detection.
4. **Edge Biometric Mesh**: AES-256-GCM envelope decryption and cosine vector matching.
5. **RAG Policy Engine**: pgvector HNSW hybrid semantic and BM25 search.

## 3. Argo Rollouts Progressive Canary Procedure

### 3.1 Step Schedule
```mermaid
flowchart LR
    A["Canary 5% (15m)"] --> B["Canary 25% (30m)"]
    B --> C["Canary 50% (30m)"]
    C --> D["Production 100%"]
```

1. **Phase 1: Canary 5% (Duration: 15 minutes)**
   - Ingress routes 5% traffic to `thaibahive-web-canary` pods.
   - Prometheus `AnalysisTemplate` checks HTTP 5xx error rate (< 0.1%) and P95 latency (< 100ms).
2. **Phase 2: Canary 25% (Duration: 30 minutes)**
   - Evaluate PgBouncer connection pool saturation and CPU/Memory usage under moderate load.
3. **Phase 3: Canary 50% (Duration: 30 minutes)**
   - Evaluate PostgreSQL write IOPS and `hardware_telemetry_buffer_size` drain metrics.
4. **Phase 4: Full Promotion (100%)**
   - Promote canary to primary stable; decommission legacy replicas.

## 4. Troubleshooting & Remediation Runbooks

### Incident 1: High Telemetry Ingestion Buffer Lag (> 500 items)
- **Symptom**: Prometheus alert `TelemetryBufferLagHigh` triggered.
- **Root Cause**: Database transaction lock contention or insufficient PgBouncer connection pool.
- **Triage Steps**:
  1. Check active database connections:
     ```sql
     SELECT count(*), state FROM pg_stat_activity GROUP BY state;
     ```
  2. Inspect PgBouncer pool status:
     ```bash
     kubectl exec -it deployment/thaibahive-db-pgbouncer -- psql -p 6432 -U pgbouncer -c "SHOW POOLS;"
     ```
  3. If `cl_waiting` > 0, scale PgBouncer pool or increase `TELEMETRY_INGESTION_CHUNK_SIZE=200`.

### Incident 2: Anti-Passback Gate False Positives
- **Symptom**: Valid students or staff members reporting `apb_violation` at turnstiles.
- **Triage Steps**:
  1. Check if the turnstile device is configured with forgiving mode or double-swipe jitter window:
     ```bash
     curl -H "Authorization: Bearer $TOKEN" https://thaibahive.example.com/api/hardware/devices/{id}
     ```
  2. If emergency egress was conducted, trigger a soft APB reset for the institution:
     ```bash
     curl -X POST -H "Authorization: Bearer $ADMIN_TOKEN" https://thaibahive.example.com/api/hardware/access-control/apb-reset -d '{"zoneId": "campus_all"}'
     ```

### Incident 3: Emergency Lockdown False Alarm Trigger
- **Symptom**: Campus turnstiles reject all standard badges with reason `Zone/Facility locked down`.
- **Triage Steps**:
  1. Inspect active lockdown status via web command center at `/operations/radar` or via REST:
     ```bash
     curl -H "Authorization: Bearer $TOKEN" https://thaibahive.example.com/api/hardware/gates/lockdown
     ```
  2. To immediately release global campus lockdown with supervisory authorization:
     ```bash
     curl -X POST -H "Authorization: Bearer $PRINCIPAL_TOKEN" https://thaibahive.example.com/api/hardware/gates/lockdown -d '{"isLocked": false, "reason": "Emergency drill concluded"}'
     ```

## 5. Emergency Rollback SOP (< 30s)

If unexpected critical anomalies occur during the canary rollout:
1. **Immediate Manual Abort via Argo Rollouts**:
   ```bash
   kubectl argo rollouts abort thaibahive-web -n thaibahive-production
   ```
2. **Revert Ingress to Stable Traffic**:
   ```bash
   kubectl argo rollouts set image thaibahive-web thaibahive-web=thaibahive/thaibahive-web:v3.37.0 -n thaibahive-production
   ```
3. **Verify Database Integrity**:
   - Because all v3.38.0 migrations follow the Expand-and-Contract backward compatibility specification, **no database rollback scripts are required**.
