# Supabase PostgreSQL Operations & Production Runbook

This runbook defines the operational standards, migration practices, backup verification, and security hardening procedures for ThaibaHive running on Supabase PostgreSQL.

---

## 1. Architecture & Connection Topologies

Supabase provides two distinct Supavisor pooling endpoints. Using the correct port for each operational role is critical to system stability:

| Role | Port | Connection Mode | Purpose / Client |
|---|---|---|---|
| **Vercel Serverless Lambdas** | `6543` | Transaction Mode | Application queries (`DATABASE_URL`). Auto-allocates short-lived connections, scaling up to thousands of concurrent serverless instances. |
| **Migrations (`db:migrate`)** | `5432` | Session Mode | DDL schema changes (`DIRECT_DATABASE_URL`). Prepared statements, advisory locks, and migration transactions require session stability. |
| **Backups (`pg_dump`)** | `5432` | Session Mode | Full logical database dumps (`scripts/db-backup.sh`). `pg_dump` requires persistent session features. |

## 2. Row Level Security (RLS) & Data API Hardening

### Why RLS is Mandatory
Supabase automatically generates a public RESTful API (PostgREST) for all tables in the `public` schema. If RLS is disabled, anyone with the public `NEXT_PUBLIC_SUPABASE_ANON_KEY` can perform unauthenticated reads and writes.

Because ThaibaHive's backend connects via Postgres pooler (`postgres` role / service connection), backend queries bypass RLS. Enabling RLS on every table without default anon policies completely locks down PostgREST while preserving backend functionality.

### Steps to Apply RLS
1. Run [`scripts/db/enable-rls.sql`](file:///d:/ThaibaHive/scripts/db/enable-rls.sql) in the Supabase SQL Editor:
   ```sql
   DO $$
   DECLARE
       r RECORD;
   BEGIN
       FOR r IN (
           SELECT tablename 
           FROM pg_tables 
           WHERE schemaname = 'public' 
             AND tablename NOT LIKE 'pg_%' 
             AND tablename NOT LIKE '_drizzle_%'
       ) 
       LOOP
           EXECUTE format('ALTER TABLE public.%I ENABLE ROW LEVEL SECURITY;', r.tablename);
       END LOOP;
   END $$;
   ```
2. In the Supabase Project Dashboard:
   - Go to **Project Settings** -> **API**.
   - Under **Data API Settings**, verify Data API is disabled if external client SDK access is not required.
3. In **Storage**:
   - Verify the `uploads` bucket is marked as **Private**.
   - All access to media/files must occur via signed URLs generated by `@thaiba/backend`.

## 3. Pre-Migration Verification & Staging Workflow

Before applying migrations to production:

### Step 1: Duplicate Check for Unique Constraints
Migration `0015_mute_kylun.sql` introduces a unique composite index on `staff_institutions(staff_id, institution_id)`. If duplicate rows exist in production, the migration will abort.

Run this audit query prior to deployment:
```sql
SELECT staff_id, institution_id, COUNT(*) 
FROM staff_institutions 
GROUP BY staff_id, institution_id 
HAVING COUNT(*) > 1;
```
If duplicates exist, deduplicate by keeping the most recent entry:
```sql
DELETE FROM staff_institutions a
WHERE a.ctid <> (
    SELECT max(b.ctid)
    FROM staff_institutions b
    WHERE a.staff_id = b.staff_id 
      AND a.institution_id = b.institution_id
);
```

### Step 2: Inspect Migration Journal
Verify current migration status in the `__drizzle_migrations` table:
```sql
SELECT id, hash, created_at 
FROM "drizzle"."__drizzle_migrations" 
ORDER BY created_at DESC 
LIMIT 10;
```

### Step 3: Run Staging Branch Test
If using Supabase Database Branching:
1. Create a preview database branch from production.
2. Run `DIRECT_DATABASE_URL=<branch_url> pnpm db:migrate`.
3. Verify zero errors and run `pnpm db:verify:columns`.

## 4. Backups and Point-in-Time Recovery (PITR)

### Automated GitHub Actions Backups
- **Database Backup**: Runs daily via `.github/workflows/db-backup.yml` using `scripts/db-backup.sh`.
  - Connects to port 5432.
  - Filters to `--schema=public --no-owner --no-privileges`.
  - Generates SHA-256 integrity checksums and syncs to encrypted S3 storage.
- **Storage Backup**: Runs weekly via `.github/workflows/storage-backup.yml` mirroring Supabase Storage buckets.

### Supabase Built-in PITR Recovery
For Pro / Enterprise Supabase tiers:
1. Navigate to **Database** -> **Backups** in Supabase Dashboard.
2. Select **Point in Time Recovery**.
3. Choose the timestamp immediately preceding the incident.
4. Restore to a new project or clone for forensic validation before updating Vercel environment variables.

## 5. Emergency Rollback & Incident Response

If a migration fails or causes unexpected locking:
1. **Identify Blocked Queries**:
   ```sql
   SELECT pid, age(clock_timestamp(), query_start), usename, query, state
   FROM pg_stat_activity
   WHERE state != 'idle' AND query NOT ILIKE '%pg_stat_activity%'
   ORDER BY query_start ASC;
   ```
2. **Terminate Hanging Lock**:
   ```sql
   SELECT pg_terminate_backend(<pid>);
   ```
3. **Rollback Script**:
   Revert schema changes using the corresponding down migration or restore from the latest automated S3 snapshot via `scripts/db/restore-backup.sh`.
